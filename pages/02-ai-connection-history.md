# 02. AI 연결 방식의 변화

AI가 외부 시스템을 사용하는 방법은 한 번에 MCP로 바뀐 것이 아닙니다. 이전 방식의 장점과 한계를 알아야 MCP가 필요한 상황을 판단할 수 있습니다.

## 네 단계의 변화

| 단계 | 사용자가 한 일 | 장점 | 한계 |
| --- | --- | --- | --- |
| 복사·붙여넣기 | 문서를 채팅창에 직접 넣음 | 가장 단순함 | 최신성·누락·개인정보 문제가 큼 |
| 검색 연동 | AI가 정해진 문서에서 검색 | 근거를 붙이기 쉬움 | 검색 외 행동은 못 함 |
| 함수·플러그인 | 정해진 API를 호출 | 실제 업무를 자동화 | 서비스별 연결과 권한 구현이 따로 필요 |
| MCP | 도구·자료·사용 규칙을 공통 방식으로 발견 | 재사용과 표준화 | 연결 서버의 보안과 품질을 검증해야 함 |

## “연결된다”의 세 가지 의미

사람들이 “AI를 연결했다”고 말할 때는 서로 다른 일을 섞어 말하는 경우가 많습니다.

| 의미 | 질문 | 예시 |
| --- | --- | --- |
| 데이터 접근 | AI가 무엇을 읽을 수 있는가? | 사내 정책 문서 검색 |
| 행동 실행 | AI가 무엇을 바꿀 수 있는가? | 일정 초안 생성 |
| 업무 위임 | AI가 여러 단계를 이어서 수행하는가? | 문의 분류 후 티켓 생성 |

MCP는 세 가지를 모두 표현할 수 있지만, 표현할 수 있다는 말과 허용해야 한다는 말은 다릅니다. 처음 도입할 때는 데이터 접근부터 시작하고, 실행 도구는 승인과 되돌리기를 설계한 뒤 추가합니다.

## 기존 플러그인과의 차이

플러그인은 특정 AI 제품 안에서 특정 기능을 제공하는 방식으로 시작했습니다. MCP는 제품보다 연결 규격을 중심에 둡니다. 따라서 같은 MCP 서버를 여러 호스트가 지원할 수 있고, 서버 작성자는 특정 대화 UI의 내부 구현에 덜 종속됩니다.

다만 호환성이 자동으로 보장되는 것은 아닙니다. 클라이언트가 지원하는 MCP 사양 버전, 인증 방식, 확장 기능, 승인 화면이 서로 다를 수 있으므로 도입 전에 확인표를 만듭니다.

| 확인 항목 | 기록할 값 |
| --- | --- |
| 클라이언트 | 제품명·버전·지원 사양 |
| 서버 | 제공하는 tools·resources·prompts |
| 전송 방식 | 로컬 프로세스 또는 원격 HTTP |
| 인증 | 사용자 로그인·토큰·OAuth 등 |
| 승인 | 자동·매번 확인·관리자 승인 |
| 중단 | 연결 해제·키 폐기·진행 중 작업 취소 |

## 최신 사양을 읽을 때 주의할 점

2026년 7월 사양은 무상태 프로토콜 코어, 요청 라우팅 헤더, 결과 캐시 힌트, 권한 강화, 장시간 작업을 위한 Tasks 확장을 소개했습니다. 이전 예제가 `initialize` 세션을 전제로 한다고 해서 현재 서버가 반드시 같은 방식으로 동작하는 것은 아닙니다. 책의 예제에는 항상 사양 확인 날짜를 표시합니다.

## 장 요약

- MCP는 복사·검색·함수 호출의 흐름을 공통 연결 규칙으로 확장한다.
- 데이터 접근, 행동 실행, 업무 위임은 서로 다른 위험도를 가진다.
- 클라이언트와 서버의 버전·인증·승인 기능을 함께 확인해야 한다.
